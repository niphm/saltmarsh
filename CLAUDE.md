# CLAUDE.md

Saltmarsh: a D&D 2024 character and party tracker (offline-first PWA, Svelte 5, Supabase later).

## Before any task

1. Read `REQUIREMENTS.md` (product requirements, phases, decisions in section 8, acceptance criteria in section 7).
2. Read `README.md` (data model and its four rules).

Section 8 of `REQUIREMENTS.md` records decisions already made. Don't re-ask them.

## Source of truth

- `schema/src/schema/` (Zod schemas) and `schema/src/engine/` (`derive()`, rests, HP) are the source of truth for data shape and rules math. Don't redesign them.
- If you find a bug in them, fix it and add a unit test that fails without the fix.
- The UI never does rules math. If a screen needs a number, it comes from the engine. If the engine can't produce it, extend the engine (with a test), not the component.
- Every trackable thing is a `Resource`. No feature-specific UI code ("if rage then...").

## After any engine change

```bash
npm run validate
npm test
```

`npm run validate` prints the derived sheet for every example in `schema/examples/`. The numbers for Tidewick and Kenpachi are the Phase 1 acceptance tests and are asserted in `schema/test/`.

## Layout

```
schema/    @saltmarsh/schema - Zod schemas, engine, examples, unit tests (npm workspace)
app/       Vite + Svelte 5 + TypeScript + Tailwind 4, PWA (vite-plugin-pwa/Workbox), Dexie
packs/     rules packs as JSON (SRD 5.2 goes in packs/srd/)
supabase/  migrations/ (all DDL and RLS), tests/rls.test.ts (security tests), config.toml (local stack)
docs/      kickoff prompt and other notes
```

Root scripts: `npm run dev`, `npm run lint`, `npm run typecheck`, `npm test`, `npm run validate`, `npm run build`.

## Supabase (Phase 2)

- Local stack (needs Docker Desktop running): `npm run db:start`, `npm run db:reset` (re-applies every migration), `npm run test:db` (RLS and realtime tests; CI runs them too and they gate deploys).
- Local dev against it: `app/.env.local` (gitignored) with `VITE_SUPABASE_URL=http://127.0.0.1:54321` and the local publishable key from `npx supabase status`. Remove it (or point it back) before building anything to compare with production.
- Schema changes are new files in `supabase/migrations/`, tested locally first. Applying one to the hosted project is a Supabase write: tell David first; he applies it (SQL editor or CLI).
- Every RLS rule gets a test in `supabase/tests/rls.test.ts`.
- Sync lives in `app/src/lib/sync/` (pure merge logic in `merge.ts`, unit-tested); party data in `app/src/lib/party.svelte.ts`. The Supabase client is loaded lazily (`lib/remote.ts`); keep it out of the first-load bundle.

## Rules packs

- `packs/<id>/pack.json` (metadata, license, attribution) plus one file per kind (`spells.json`). Entries are keyed `pack:kind:slug`.
- `packs/srd/spells.json` is generated by `npm run packs:srd` from Open5e's SRD 5.2 data. Don't hand-edit it; fix the build script.
- Only SRD 5.2 content goes in `packs/srd/` (verify against the SRD; Open5e document key `srd-2024`). Non-SRD content the party uses goes in `packs/saltmarsh/` with original summaries, never book text.
- The SRD attribution in `packs/srd/pack.json` is shown in Settings > About and must stay.

## Conventions

- Commit small and often with conventional-commit messages (`feat:`, `fix:`, `test:`, `chore:`, `ci:`, `docs:`, `refactor:`).
- Mobile first: check every screen at 390px width before desktop. Tap targets at least 44px.
- Tailwind and hand-written Svelte components only. No UI component kits. Prefer boring, well-documented libraries.
- Themes are CSS custom-property sets in `app/src/themes/*.css`, one file per theme, no per-theme component changes. Every theme must pass the contrast test in `app/test/themes.test.ts`.
- Vite `base` and PWA scope are `/saltmarsh/`. Live at https://niphm.github.io/saltmarsh/.
- When a requirement is ambiguous, pick the option that keeps the UI ignorant of D&D rules, and say what you picked.

## Audits (re-run after UI changes)

- Contrast: `app/test/themes.test.ts` (AA for every theme, AAA for High Contrast, status colors distinct).
- axe: `npm run build`, copy `node_modules/axe-core/axe.min.js` into `app/dist/`, serve the build, load `/saltmarsh/axe.min.js` in the page and `axe.run()` on each screen and open dialog. Target: zero violations.
- Lighthouse (mobile, simulated slow 4G): `npx lighthouse@13 http://localhost:4173/saltmarsh/ --form-factor=mobile`. Lighthouse 12+ has no PWA category; `npx lighthouse@11.7.1 ... --only-categories=pwa` checks installability.
- Last run (2026-11-08, Phase 2): axe 0 violations on every screen and dialog, including account, party, inventory and journal (run against the dev build; injecting axe from a CDN into the live page is blocked). Lighthouse on the live site 100/100/100/100, FCP 1.5 s, LCP 1.5 s, CLS 0, TBT 0 ms. PWA (v11) 100 as of 2026-11-07.
- Never put deep `$state` objects into the store or IndexedDB (DataCloneError on proxies): use `$state.raw` or `$state.snapshot`.

## Never without telling the user first

- Writing to Supabase (schema, data, auth settings).
- Changing GitHub repo settings or secrets.
- The Supabase service_role key is never used. Everything goes through RLS with the publishable key.
